## CONVENTIONS
- **NNN_short_name.py** — three-digit prefix, snake_case slug. Don't use Alembic's default UUID-prefix style; it breaks the visual ordering convention.
- **Down revisions point at the file, not just the SHA.** Autogenerate handles this; don't hand-edit.
- **One concern per migration.** Schema change + data backfill = two migrations (or one with a clearly separated `op.execute(...)` block).
- **Vietnamese / English text in `op.execute(...)`** is fine — the DB is UTF-8. Don't transliterate.
- **Native enums via `op.execute("CREATE TYPE ... AS ENUM (...)")`** for status/priority columns. Mirror in the model with `sqlalchemy.Enum(..., native_enum=True, create_type=False)`.

## WORKFLOW
```bash
# 1. Edit app/database/models.py
# 2. Generate
alembic revision --autogenerate -m "short message"
# 3. REVIEW the generated file — autogenerate misses:
#    - column renames (it sees drop+add)
#    - check constraints
#    - enum value additions on existing types
#    - data migrations
# 4. Apply locally
alembic upgrade head
# 5. Test downgrade if it's reversible
alembic downgrade -1 && alembic upgrade head
# 6. Commit BOTH the model change and the migration
```

## ANTI-PATTERNS
- **Don't edit a merged migration.** The whole `001..018` chain is sealed. Add a new migration to fix a bug.
- **Don't squash old migrations** — production deployments replay them in order from whatever revision they're on.
- **Don't `op.execute("DROP TABLE ...")` without a downgrade path.** If you really must drop, write the recreate in `downgrade()`.
- **Don't run `alembic stamp head`** to "skip" migrations on a real DB — it desyncs schema from migration state silently.
- **Don't put data fixtures here.** Reference data (provinces, VSIC codes) lives in `app/data/*.json` and is loaded at runtime.
